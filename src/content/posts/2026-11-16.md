## [PHP 8.6.0RC7 is available for testing](https://externals.io/message/133088)

PHP 8.6 の正式リリース直前の最終チェック版（RC7）が出ました。GA（正式版）は11月19日予定。RC は「問題がなければこのまま正式版にする」候補版で、今はバグ出しの最終段階です。

感想：もうすぐ 8.6 が来ます。新機能を追うより、まず自分の環境で動くか試す時期ですね。

## [[RFC] Sunset PECL](https://externals.io/message/133008)（[RFC wiki](https://wiki.php.net/rfc/sunset_pecl)）

PECL は PHP の拡張機能（追加モジュール）を配る老舗サイトです。新しい配布の仕組み PIE に役目を譲り、非推奨になっていましたが、この RFC は「いつ、どうやって完全に閉じるか」の日程案です。2027年中に読み取り専用化→段階停止→閉鎖、という計画。議論では「読み取り専用の期間に拡張の脆弱性が見つかっても、誰も直せなくなるのでは」という指摘が出ています。

感想：PECL 経由で入れた拡張が残っているサーバーは多いはずで、移行先の確認は早めに必要そう。閉鎖そのものより、その指摘のセキュリティ問題の方が本題だと思います。

## [[RFC] Vetting cURL connections with CURLOPT_OPENSOCKETFUNCTION](https://externals.io/message/133085)（[RFC wiki](https://wiki.php.net/rfc/curl_opensocketfunction)）

SSRF という攻撃への対策です。SSRF は「URLを指定するとサーバーが取りに行く」機能を悪用して、外部向けのつもりが社内ネットワークなど内部にアクセスさせられる攻撃。URL の文字列チェックだけでは、DNS のすり替えなどで簡単にすり抜けられます。この RFC は、実際に接続する瞬間の IP アドレスを見て「そこに繋いでいいか」をプログラム側で判定できる仕組みを追加します。議論を経て API はシンプルな形に改められました。

感想：SSRF は実務で本当に踏みやすい穴なので、接続直前に止められるのはかなり実用的。PHP 8.3〜8.6 用のポリフィル（先行実装）まで用意されているのも好感が持てます。

## [[Pre-RFC] Honour Linux AT_EXECVE_CHECK: W^X for PHP scripts](https://externals.io/message/133055)

W^X は「メモリやファイルは、書けるものは実行できない・実行できるものは書けない」という分離の原則で、攻撃の足場を減らす考え方です。Linux の新しい仕組み（カーネル 6.14 の AT_EXECVE_CHECK）でシステム全体にこの方針が設定されている場合、PHP スクリプトの実行や対話モードのコード実行もそれに従うようにしよう、という提案。設定されていない環境では今まで通りです。

感想：かなり玄人向けで、普通のアプリ開発ではまず縁がない話。ただ「PHP だけポリシーの抜け穴になる」状態を塞ぐ意味では筋がいいと思います。

## [[RFC] Prepared Literal String Matching and Replacement](https://externals.io/message/133028)（[RFC wiki](https://wiki.php.net/rfc/prepared_literal_string_matching)）

大量のキーワードで大量のテキストを検索・置換する処理を高速化する新機能の提案です。例えば NG ワードが何千語もあるコメントのモデレーションや、User-Agent 文字列からのボット判定など。「辞書を先に準備しておく」ことで、既存のやり方の8〜123倍速くなるというベンチマークが出ています。レビューを受けて測定方法の見直しなど v0.4 まで改訂が進んでいます。

感想：用途はピンポイントですが、刺さる現場には強烈に刺さるタイプ。常駐ワーカー型の PHP が増えている流れとも合っています。

## [[RFC] Context Managers, v2](https://externals.io/message/133003)

Python の `with` 文のような仕組みを PHP に入れる提案の第2版です。「ファイルを開いたら必ず閉じる」「接続したら必ず切断する」のような、開始と後片付けがセットの処理を、ブロックで囲むだけで自動化できるようになります。今でも try-finally で書けますが、定型コードが減って読みやすくなるのが狙いです。

感想：便利なのは分かるけど、「try-finally で書けることを言語機能にする価値があるか」が問われる提案。賛否が割れるタイプだと思います。

## [[RFC] grapheme_str_pad()](https://externals.io/message/132995)（[RFC wiki](https://wiki.php.net/rfc/grapheme_str_pad)）

文字列を指定の長さまで埋める `str_pad()` の「見た目の文字数」版です。日本語の濁点（「か」に点々を合成する形式）や絵文字の組み合わせは、内部的には複数コードでも人間には1文字に見えます。既存の関数はここを正しく数えられず、桁揃えがズレることがありました。この提案は「人間が見た1文字」単位で数える版を追加します。

感想：日本語を扱う私たちには一番身近な話題かもしれません。地味ですが、こういう国際化の穴埋めは大事。

## [[RFC] Request lifecycle hooks for SAPIs with a worker mode](https://externals.io/message/133044)

FrankenPHP や RoadRunner のような「PHP を常駐させてリクエストを次々処理する」実行方式向けの提案です。従来の PHP はリクエストごとに起動して使い捨てる前提でしたが、常駐型では「リクエスト開始・終了」のタイミングを拡張機能側に知らせる仕組みが必要で、それを追加しようという話。今週は既存の拡張が無変更で動き続ける設計であることが確認されました。

感想：PHP の実行モデルが静かに変わっていく象徴的な議論。常駐型を使う現場では地味に重要な土台です。

## [LoongArch64 backend for the OPcache JIT](https://externals.io/message/133074)

LoongArch64 は中国発の CPU アーキテクチャです。PHP の高速化機能 JIT は今のところ x86 と ARM 系にしか対応しておらず、この CPU では使えません。対応を追加したいが、数千行規模の低レイヤ実装になるので、着手前に「やっていいか、どう進めるか」を相談するスレッドです。実機でのテスト環境はあるとのこと。

感想：実装そのものより「誰が将来まで保守するのか」が論点になりそう。中国市場向けハードの存在感が PHP の中にも出てきたな、という一件です。

## [IPv6-capable hostname lookup in ext/standard](https://externals.io/message/133097)

ホスト名から IP アドレスを引く標準機能が IPv6 にきちんと対応していない部分があり、それを埋める提案です。他の種類の DNS レコード取得は既存の `dns_get_record()` の担当として範囲を広げず、既存の接続処理と揃えた設計に留める方針が確認されています。

感想：派手さはないけど、IPv6 が当たり前になる中で標準関数の穴は確実に困る人が出ます。範囲を欲張らない姿勢も PHP らしい。
