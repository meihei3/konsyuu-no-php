## [PHP 8.6.0 Released](https://externals.io/message/133121)（[リリース告知](https://www.php.net/releases/8_6_0.php)）

PHP 8.6 の正式版が11月19日に出ました。目玉は部分関数適用（引数の一部だけ先に決めて、残りを受ける関数を作る書き方）、readonly プロパティへのデフォルト値、ストリームの待ち受けをする新しい `Io\Poll` API、値を範囲内に収める `clamp()` 関数、ナノ秒精度の時間の長さを表す `Time\Duration` クラス、並び順を表す `SortDirection` enum です。バグ修正は2028年12月31日まで、セキュリティ修正は2030年12月31日まで提供されます。

同じ日には 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 のセキュリティリリースも同時に出て、17件の脆弱性（うち7件が critical）が修正されました。なかでも注目は「phpAfterShell」と呼ばれる PHP-FPM のリクエストスマグリング（CVE-2026-129289）で、FastCGI の接続を使い回す設定だと、前のリクエストの残りが次の偽のリクエストとして読まれてコード実行につながる恐れがあるものです。8.6 に上げる予定がなくても、使っているブランチのセキュリティリリースへの更新は急いだ方がよさそうです。

感想：ついに 8.6 が来ました。ただ今週の主役は新機能よりセキュリティリリースの方かもしれません。FPM の接続再利用という、ふだん意識しない設定が攻撃の入口になるという話は、自分のサーバー設定を点検するきっかけになりますね。

## [[VOTE] [RFC] grapheme_str_pad()](https://externals.io/message/133116)（[RFC wiki](https://wiki.php.net/rfc/grapheme_str_pad)）

先週紹介した `grapheme_str_pad()` の RFC が投票に入りました。締切は12月2日 16:00 UTC、可決には3分の2の賛成が必要です。`str_pad()` の「人間が見た1文字」単位版で、日本語の濁点や絵文字の組み合わせなど、内部的には複数コードでも見た目は1文字、という文字列の桁揃えを正しく扱えるようにする提案です。

感想：先週「日本語を扱う私たちには一番身近」と書きましたが、そのまま投票に進んだのは順調な流れ。桁揃えのズレは地味に遭遇するので、通ってほしい一件です。

## [Docker images for 8.6 now default to ZTS](https://externals.io/message/133140)

Docker の公式 PHP イメージが、8.6 から ZTS ビルドを既定にしたことをめぐる騒動です。ZTS（Zend Thread Safety）はスレッドセーフなビルドで、ふつうの PHP-FPM 運用では不要なもの。Docker 側は「PHP プロジェクトからの公式の要請」と受け取って切り替えたのですが、PHP 側のリリースマネージャーは「そんな要請はしていない」と困惑し、メーリングリストでプロセスの問題として議論になりました。Docker 側は既定を戻す方向の対応を進めています。

感想：「公式イメージ」と「PHP 公式のイメージ」は別物、という当たり前の話が、現実にはここまでこじれるのか、という一件。`docker pull php:8.6` をそのまま使っている人は、自分のイメージが ZTS かどうか一度確認した方がよさそうです。

## [PHP.net homepage redesign — feedback requested](https://externals.io/message/133147)

PHP の公式サイト php.net のトップページを刷新する案が出て、広く意見が求められています。PHP Ambassadors のマーケティンググループが作ったもので、ライブプレビューと PR（php/web-php #2105）が公開済み。狙いは「初心者にも分かりやすく、モダンな PHP の魅力を伝える」ことで、既存開発者向けの使い勝手も残す方針です。最低2週間の議論期間を設け、年末までの公開を目指しています。反応はおおむね好意的で、「緊急のセキュリティ通知をどう見せるか」「PHP のブランドカラーの紫が薄い」「ダークモード切替ボタンにラベルがない」といった指摘が出ています。

感想：php.net のトップは長年ほぼ変わらない顔だったので、刷新の動き自体が新鮮です。ただ、このブログがモノクロにこだわっているのとは対照的に、こちらは「紫が足りない」と言われるあたり、色の扱いの難しさを感じます。

## [Common-sense security hardening for the next PHP](https://externals.io/message/133123)

PHP 9 に向けたセキュリティ強化の大胆な提案です。Greg Magarshak 氏の案は「`include` / `require` は `.php` と `.phar` しか読み込めないようにし、書き込み系の関数は `.php` / `.phar` への書き込みを拒否する」というもの。つまり「実行できる場所」と「書き込める場所」を分ける（W^X という考え方）ことで、攻撃者がアップロードしたファイルを PHP として実行させる手口を塞ごう、という発想です。あわせて、ヒアドキュメントに「この文字列は開発者が書いたもの」という出自を持たせ、`eval()` や `exec()` に渡せるのはその文字列だけにする案も出ています。

反論も活発です。Twig や Blade といったテンプレートエンジンはテンプレートを `.php` にコンパイルして `include` するので壊れてしまう、ストリームラッパーやシンボリックリンク、SQLite や GD など迂回路が多すぎる、OS レベルの W^X（先週紹介した AT_EXECVE_CHECK の Pre-RFC）と何が違うのか、といった指摘が並びました。

感想：「常識的な強化」というタイトル通りの、素朴で分かりやすい提案。だからこそ反論も分かりやすく、どこまでを言語の責任にしてどこからを運用の責任にするか、という PHP らしい境界線の議論になっています。個人的には、テンプレートエンジンへの影響の指摘が一番重いと感じました。

## [[RFC] [Discussion] #[\Deprecated] for interfaces](https://externals.io/message/133174)（[RFC wiki](https://wiki.php.net/rfc/deprecated_interfaces)）

インターフェースに `#[\Deprecated]` 属性を付けられるようにする RFC の議論が始まりました。`#[\Deprecated]` は「この機能は非推奨ですよ」とマークする目印で、PHP 8.4 で関数などに導入され、8.5 で定数やトレイトにも広がりました。今回はインターフェースが対象で、非推奨とマークされたインターフェースを実装したり継承したりすると警告が出ます。ただし `instanceof` でのチェックや型宣言で使うだけでは警告は出ません。RFC は5月に作られたもので、対象バージョンは PHP 8.7 です。

感想：ライブラリ作者にとっては「このインターフェースはもう使わないで」と伝える手段が増える、地味にうれしい話。警告が出る場面を「積極的に使うとき」だけに絞っている設計も筋がいいと思います。

## [[Pre-RFC] Lazy iterator_* functions for iterables](https://externals.io/message/133181)

ジェネレータ（値を少しずつ生み出す仕組み）などに対して、遅延評価の `iterator_*` 関数を11個追加する Pre-RFC です。今の `array_*` 関数は配列しか受け付けないので、ジェネレータを扱うには `iterator_to_array()` で一度全部配列にする必要があり、メモリを食う・途中で止められない・無限のデータ源には使えない、という問題があります。この提案は `iterator_map` / `iterator_filter` / `iterator_slice` などの遅延版（結果もイテレータで返す）と、`iterator_reduce` / `iterator_any` / `iterator_find` などの終端版を用意し、パイプ演算子（PHP 8.5）や部分関数適用（PHP 8.6）と組み合わせて、データを少しずつ流しながら処理できるようにします。C 言語での実装やポリフィル、ベンチマークまで用意済みで、500万行の NDJSON を処理する例ではメモリ使用量が 3.1GB から 11KB になったとのことです。

感想：初投稿の方が実装まで持ってきた完成度の高い提案。パイプ演算子と部分関数適用が揃った 8.6 の今だからこそ意味が出てきた、というタイミングの良さも感じます。名前の付け方（`iterator_` 接頭辞か名前空間か）が議論の焦点になりそうです。

## [[RFC] [Discussion] Enable selecting a group by column name in PDO::FETCH_GROUP](https://externals.io/message/133179)

データベースの結果をグループ化して取り出す `PDO::FETCH_GROUP` で、グループ化のキーにするカラムを名前で指定できるようにする提案です。今は「SELECT の先頭カラム」で固定されていて、別のカラムで分けたいときはクエリの書き方を工夫するしかありません。`fetchAll()` に第2引数を追加する試作が進んでいますが、存在しないカラム名を指定されたら例外にするか無視するかなど、まだ決まっていない点も多く、議論のごく初期段階です。

感想：PDO を使う人には「ああ、たしかに先頭カラム縛りは不便」と共感できる話。ただ提案自体はまだ荒削りで、これからどこまで詰まるか見守り、という段階です。

## [[Proposal] OPcache: share identical opcode arrays between cached scripts (opcache.enable_dedup)](https://externals.io/message/133048)

前回号（11/10投稿）で拾い漏らしていた提案を今週補足します。共有ホスティングなどで同じアプリのコピーが多数動いていると、OPcache（PHP の実行コードをキャッシュする仕組み）が同じバイトコードをコピーごとに別々に保持してメモリを食い潰す、という問題があります。この提案は、内容が同一の opcode 配列（コンパイル済みの命令列）を共有する `opcache.enable_dedup` という設定（既定は無効）を追加するものです。80の WordPress サイトでの負荷試験では OPcache のメモリが 6,406MB から 3,428MB（-46.5%）になり、実運用でも -43% が報告されています。新しい設定の追加なので RFC が必要か、PR での議論で十分か、という進め方の相談も含まれています。

感想：共有サーバーを運用する人には刺さる、数字の説得力が強い提案。ただ「共有する」ことのセキュリティ面（1つの書き込みが全サイトに波及する）への目配りも書かれていて、慎重な設計だなと感じました。
